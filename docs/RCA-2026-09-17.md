# RCA — 2026-09-17: no orders placed, no 20:30 screener

Two unrelated-looking failures on the same day turned out to share one cause:
**the same service is deployed three different ways on one VM, and nobody
owns which one is authoritative.**

- **Incident A** — four confirmable orders expired unconfirmed. `placed_count: 0`.
- **Incident B** — the 20:30 IST screener never delivered to Telegram.

Neither was caused by what it looked like. Incident A was not the IPv6 /
dual-IP problem. Incident B was not a wrong cron schedule.

All times below are **IST**; the VM runs UTC, so subtract 5h30m for anything
you read in `journalctl`, `docker logs`, or `crontab`.

---

## Incident A — orders never placed

### What it looked like

"The machine had dual IP, so orders were rejected by Kite this morning."

That is a real problem, and it was real *earlier*. It is not what happened
today. Today the orders **never reached Kite at all** — they were never
confirmed, so `place_order` was never called. An IP whitelist rejection
cannot occur on a request that was never sent.

Evidence: `KITE_FORCE_IPV4: DNS/API calls will use IPv4 only` is logged at
watcher startup, so the IPv4 pin was active. `.nse_alert/orders.json` shows
`placed_count: 0` and five orders stuck in `pending` — not `rejected`,
not `failed`. **Pending means the confirmation never arrived.**

### What actually happened

`TRADE_MODE=confirm` requires you to reply in Telegram to release an order.
The listener receives that reply by long-polling `getUpdates`.

**Telegram allows exactly one `getUpdates` consumer per bot token.** A second
consumer causes every poll to fail:

```
409 Conflict: terminated by other getUpdates request;
make sure that only one bot instance is running
```

Two watcher processes were running against the same bot token. Every poll
returned 409. The confirm listener **never successfully received a single
update all day** — so your replies went nowhere, and all four orders aged out
at their 30-minute TTL.

Outbound alerts kept working throughout, which is why this was invisible:
`sendMessage` has no such restriction. **The bot could talk to you; it could
not hear you.**

confirm path was already dead when those orders were created.

### Root cause

Three overlapping deployment mechanisms exist for one service:

1. **systemd** — `deploy/nse-alert.service`, `enabled`, starts at boot
2. **Docker** — `docker-compose.yml`, `restart: unless-stopped`
3. **Bare host** — `uv run nse-alert watch`, documented in the README

All three are documented as valid. Nothing prevents two from running at once,
and both systemd and Docker restart themselves automatically. As of this
writing **both are running simultaneously**:

```
PID 3393  /opt/nse-alert/.venv/bin/python .../nse-alert watch   (systemd, since 14:06)
PID 4139  /app/.venv/bin/python .../nse-alert watch             (docker,  since 16:47)
```

### Contributing factors

- **No alert on a broken listener.** 5,994 consecutive failures logged at
  `WARNING`, never surfaced to Telegram. The one channel guaranteed to reach
  you was the one not used.
- **Silent expiry.** Orders expire with no notification. A "3 orders expired
  unconfirmed" message would have exposed this within 30 minutes.
- **Stale Kite token at 09:30**, independent of the above, degraded sizing on
  the first order.

### It was not "docker started twice"

The natural reading is that the container got launched twice during debugging.
The evidence says otherwise, and the distinction decides the fix.

`PID 3393` has cgroup `/system.slice/nse-alert.service` and parent PID 1 — it
is the **systemd unit**, not a container. `PID 4139`/`9599` is the Docker
container (`docker top` confirms). One of each, never two containers.

The systemd unit is `enabled`, i.e. `WantedBy=multi-user.target`, so it starts
a watcher **on every boot**, with `Restart=on-failure`. It also reads the same
`EnvironmentFile=/opt/nse-alert/.env`, so it picks up the daily Kite token too
and looks healthy.

This means the daily workflow — login, get token, `docker compose up`, close
the tab — **cannot avoid the conflict by being careful**. However disciplined
the Docker step is, systemd has already started a second watcher by itself.
The operator error was not running a command twice; it was that two
always-on supervisors both own the same service.

### Config drift (updated 22:07 IST)

At 22:00 IST the container was recreated and picked up `TRADE_MODE=auto` from
`.env` (edited 18:16 IST). The systemd watcher still runs `trade=confirm` —
it started at 14:06 IST and does not reload `.env`.

The two watchers are now in **different modes**:

| Watcher | Mode | Confirm listener |
|---------|------|------------------|
| Docker (PID 9599) | `auto` | no |
| systemd (PID 3393) | `confirm` | yes |

The 409 storm stopped at 22:00 IST — not because anything was fixed, but
because `auto` mode starts no confirm listener, leaving systemd as the only
poller. The underlying dual-watcher condition is unchanged.

**This is a live risk for the next open.** Both watch the same universe. A
single ±13% move can produce an automatic order from the container *and* a
confirmation prompt from systemd — and confirming that prompt places a
**second** order for the same signal. `orders.json` is shared via the
bind-mount but has no cross-process locking, so `TRADE_MAX_ORDERS_PER_DAY`
is not a reliable backstop against the race.

## Incident B — 20:30 screener never delivered

The cron schedule was correct all along: `0 15` UTC **is** 20:30 IST, and
syslog confirms it fired at `15:00:01` UTC. Two stacked bugs killed it after
it fired.

**B1 — `uv` not on cron's PATH.** Cron does not source `.profile`, so it ran
with a bare `/usr/bin:/bin` and never saw `/home/ubuntu/.local/bin/uv`:

```
/bin/sh: 1: uv: not found
```

**B2 — root-owned output file.** `Dockerfile` sets no `USER`, so the container
runs as root and writes into the bind-mounted `./.nse_alert`. A manual
`docker compose run` of the screener at 17:18 IST left `screen-2026-09-17.xlsx`
owned by root. The cron runs as `ubuntu`:

```
PermissionError: [Errno 13] Permission denied:
'.nse_alert/screener/screen-2026-09-17.xlsx'
```

B2 was hidden behind B1 — fixing PATH alone would have failed again, after a
full 4-minute scan, at the very last write.

**B3 — the repo is broken on `main`.** Commit `b2c6e9f` replaced an import
instead of adding one:

```diff
-from nse_alert.config import Settings
+from nse_alert.ipv4 import force_ipv4
```

`cli.py` uses `Settings` 17 times and nothing imports it. Every command that
builds settings raises `NameError`. Only `--help` survives. The VM works only
because of an **uncommitted one-line patch on that one box**. A fresh clone,
or a VM rebuild from `main`, is completely non-functional.

The same commit that fixed the IPv6 problem introduced B3. **The morning's fix
caused the evening's outage.**

---

## Systemic causes

1. **Three deployment paths, no single source of truth.** Direct cause of A;
   B2 is the same collision expressed as file ownership.
2. **Failures logged, never alerted.** Both incidents ran for hours in plain
   sight. A Telegram bot was right there.
3. **A hotfix applied to the VM and never committed.** Production and `main`
   silently diverged; `main` is the broken one.
4. **Tests did not catch a repo-wide `NameError`.** No test exercises a real
   command path.
5. **Timezone ambiguity.** The box is UTC, requirements are in IST, and the
   docs' own example (`15 16 * * 1-5`, commented "16:15 IST") actually fires
   at 21:45 IST.
6. **Silent config drift.** `.env` edits do not reach running processes and
   nothing reports the mismatch.

## Actions

Ordered by leverage. P0/P1 prevent recurrence; the rest are hardening.
Repo-side fixes are detailed in [`../FIX_PLAN.md`](../FIX_PLAN.md).

### P0 — Pick one deployment mechanism

Choose **one** of systemd or Docker. Docker is the better default: the
container already carries its dependencies and the compose file is the more
maintained artifact.

```bash
sudo systemctl disable --now nse-alert   # if standardising on Docker
```

Then delete the unused path and update `README.md` + `deploy/CLOUD.md` so only
one method is documented as production. Note the bare `uv run nse-alert watch`
in the README is a third path — mark it local-testing-only.

**Done 2026-09-17:** `deploy/nse-alert.service` deleted; Docker documented as
the only production path.

**Verify exactly one watcher** — must print exactly one line:

```bash
ps -eo cmd --no-headers | grep "[.]venv/bin/python .*nse-alert watch"
```

Do not use `pgrep -f "nse-alert watch"` for this: it matches its own command
line (and any shell wrapping it) and over-counts.

### P0 — Refuse to start a second poller

A process-level guard so this cannot recur regardless of deployment. On
listener start, take an exclusive lock (`flock` on a file under `STATE_DIR`,
or a `SO_REUSEADDR`-free localhost port bind). If it is held, log an **error**
and exit non-zero rather than polling into a 409 loop.

**Done:** `nse_alert/lock.py` — `watch` acquires an exclusive `flock` on
`STATE_DIR/watch.lock` before any Telegram/Kite setup and exits non-zero if
another instance already holds it. See [`PREVENTION_PLAN.md`](../PREVENTION_PLAN.md) P1.

### P0 — Alert on a dead confirm listener

Treat repeated `getUpdates` failure as an incident, not a warning:
after N consecutive failures (say 3), send **one** Telegram message —
`sendMessage` works even when `getUpdates` is 409-locked, which is exactly
what makes this reliable — then back off. Never let it fail silently 5,994
times again.

**Done:** `TelegramConfirmListener` counts consecutive `getUpdates` failures
(HTTP errors and Telegram `ok:false` responses both count) and sends one
Telegram alert via the existing `TelegramNotifier` on the 3rd, logged at
`ERROR`. It backs off exponentially (capped at 5 min) instead of hammering a
dead poll, and does not alert again until a poll succeeds. See
[`PREVENTION_PLAN.md`](../PREVENTION_PLAN.md) P2.

### P1 — Notify on order expiry

When a pending order expires unconfirmed, post to Telegram. This alone would
have caught Incident A inside 30 minutes.

### P1 — Fix `main` and commit the stranded hotfix

See `FIX_PLAN.md` P0. Add a `CliRunner` smoke test over every command plus one
test that constructs `Settings()` through a real command path.

### P1 — Make the container write as `ubuntu`

`user: "1000:1000"` in `docker-compose.yml`, so host and container stop
fighting over `.nse_alert/`. See `FIX_PLAN.md` P1.

### P2 — Restart after `.env` changes, and log the mode

Add a note to `docs/ORDERS.md` that `TRADE_MODE` changes need a restart. On
startup the watcher already logs `trade=...` — make that easy to check, and
consider having the EOD report state the mode it ran under.

**Do this now:** `TRADE_MODE=auto` is not live on either running watcher.

### P2 — Standardise on UTC-with-IST-comments in cron

Codify the working crontab (including the `PATH=` line) in `deploy/CLOUD.md`,
annotate each entry with both UTC and IST, and state plainly that Lightsail is
UTC. Fix the misleading `15 16 * * 1-5` example. See `FIX_PLAN.md` P2.

### P2 — Daily heartbeat

One Telegram message per trading day summarising: watcher mode, alerts fired,
orders placed/expired, screener status. Silence then becomes a signal. Both of
today's incidents were *absences* of messages, which is precisely what a human
does not notice.

### P3 — Kite token freshness check

The 09:30 order sized against a stale token. Validate the token at startup and
before the first order of the day; alert on failure rather than falling back.

**Done:** `watch` calls `kite.profile()` at startup and exits with a Telegram
alert on `TokenException`, before any universe/feed setup. `order_margins`
failing mid-session with a `TokenException` now raises `SizingRefusedError`
(refuse + alert, skip just that trade) instead of falling back to an
approximate leverage estimate — the fallback still applies to non-auth
failures (network blips etc.), which is the correct behavior for those. Also
switched `docker-compose.yml` from `restart: unless-stopped` to
`restart: on-failure:3` so a credential error that can't self-heal produces a
visibly stopped container instead of an endless silent restart loop. See
[`PREVENTION_PLAN.md`](../PREVENTION_PLAN.md) P4.
